# Operations publish the codes they refuse with: implementation plan

DATE: 2026-10-02
STATUS: Scoped. Ed decided D1 to D4 on 2026-10-02, each as recommended. Not yet authorized for
implementation.
AUTHOR: Ed May, BLDGTYP, with Claude
ISSUE: https://github.com/bldgtyp/ph-composer/issues/39

Read [README.md](README.md) first for the required behavior. Facts below are from `main` at 6e3f5b0.

## Starting point

- Features declare codes with `feature.code(code, description:)` (`shell/registry.rb:397`), each
  feature from a `codes.rb` table: `features/zones/codes.rb`, `features/assemblies/codes.rb`,
  `features/windows/codes.rb`. `CodeValidation` (`shell/registry_validation.rb:386-420`) checks the
  `noun.condition` shape, a description, one owner per noun, no repeat, and no foundation noun.
- Foundation and shared-noun codes have **no Ruby list**. They live in the table in
  `context/CONTRACTS.md`, "Outcomes and codes". Ruby knows only their nouns,
  `Declarations::FOUNDATION_CODE_NOUNS`. `tests/outcome_codes_test.rb` parses the table, asserts the
  nouns match the constant (lines 30-31), and fails when source names a code that is neither listed
  nor declared.
- Five operation kinds register through `query`, `action`, `view_command`, `setup_command` and
  `file_export` (`shell/registry.rb:280-323`): 32, 44, 11, 4 and 1 registration call sites, some in
  loops, about 130 operations in all.
- `API.describe` builds every kind's answer in one method, `operation_description`
  (`shell/api.rb:155-167`). The export task methods are described separately by
  `Export::TaskContract.describe`.
- Every refusal from dispatch passes through `Dispatch#coded_outcome` (`shell/dispatch.rb:401`),
  reached from eight `rescue CodedError` sites. It has the error and the session, not the declaration.
- `docs/API_REFERENCE.md` is generated by `tools/api_reference/api_reference.rb`; `operation_section`
  prints each operation. "Feature codes" lists the declared codes by feature.

## Scope corrections to the README

- The README says "a query or action". `describe` answers all five kinds in one shape, so `refuses:`
  goes on all five; otherwise a caller sees two shapes.
- `feature.code` declares finding codes and refusal codes together. `refuses:` lists refusals only:
  an outcome whose `status` is not `completed`. A code that arrives in `findings` on a completed
  outcome is not a refusal. Publishing an operation's finding codes (`reports:`) is out of scope.
- Export task methods (`start_export` and the rest) are out. They are described by their own
  contract, raise `Export::Blocked` outside dispatch's declarations, and
  [agent-authorized-file-access](../agent-authorized-file-access/PLAN.md) Phase 5 may reshape
  `start_export`. Revisit after that lands.

## Decisions

Ed decided all four on 2026-10-02, each as recommended: D1 required (optional only during the
rollout phases); D2 the `FOUNDATION_CODES` constant mirrored by test; D3 a common set per kind,
published once; D4 the test-only refusal audit.

**D1. Required or optional.** Recommendation: required on every operation, with `refuses: []` as an
explicit "nothing beyond the common set". Optional means a contributor skips it and `describe` is
unreliable for exactly the operations an agent does not know.

**D2. A Ruby list of foundation codes.** Registration must recognize `target.not_found` in a
`refuses:` list. Recommendation: `Declarations::FOUNDATION_CODES`, a frozen array of the table's
codes, with `tests/outcome_codes_test.rb` asserting it equals the CONTRACTS.md table (the pattern the
test already uses for the nouns). The table stays the readable authority; the constant is what code
checks against. Alternative: accept any code under a foundation noun. That lets a typo such as
`target.not_fond` through.

**D3. Codes every operation of a kind can answer belong to dispatch.** Dispatch raises
`request.*`, `session.*`, `params.invalid`, `revision.stale`, `proposal.changed`,
`operation.failed`, `operation.rollback_unverified`, `access.user_required`, `request.cancelled` and
the retry codes for whole kinds, not per operation. Recommendation: a foundation-owned
`Dispatch::COMMON_REFUSALS`, keyed by kind (actions also answer the retry and revision codes;
declarations with an `approval` also answer the access codes). `discover` publishes it once as
`common_refusals`. An operation's `refuses:` lists only what its handler and its dependencies
raise. `describe` returns `refuses` (the operation's own, each with `code`, `owner`, `description`)
and `common_refusals_kind` naming which common set applies, so a caller sees the full answer in two
reads without 130 copies of the same eight codes. This also keeps the README's
`make fixtures-check` expectation true: the reference changes only by the added per-operation lists.

**D4. Completeness, not just validity.** Registration can prove each listed code exists; nothing
proves an operation lists every code it raises. A static scan does not work, because handlers raise
from shared modules (`Records::Engine`, locators, participants). Recommendation: pass the
declaration into `coded_outcome`, and give dispatch a refusal audit hook that is nil in production.
The offline test helper installs a collector that fails the run when a refusal's code is outside
the operation's `refuses:` plus its common set. Coverage then decides how complete the lists are,
which matches how the suite already guards other contracts. Alternative: validity only, as the README
states. Cheaper, and the lists drift.

## Phases

One branch, one commit per phase, focused tests per phase, `make ci` at the end.

### Phase 1. The declaration and its validation

- Add `refuses` to the `Query`, `Action`, `ViewCommand`, `SetupCommand` and `FileExport` structs
  (`shell/declarations.rb`) and a `refuses:` keyword to the five registration methods. Under D1 it is
  required; while Phase 3 is in progress the default is `nil` ("not yet declared") so the batch can
  land in steps, and Phase 4 removes the default.
- `Declarations::FOUNDATION_CODES` (D2) and its equality assertion in `tests/outcome_codes_test.rb`.
- `CodeValidation` gains `check_refusals`: each entry is a string, unique in its list, and either in
  `FOUNDATION_CODES` or declared by a feature in the live registry or this batch. An entry in the
  kind's common set is refused as redundant, so the per-operation lists stay specific. Diagnostic:
  `registration.schema_invalid`, naming the operation and the code.
- Tests (`tests/registry_test.rb`): a declared feature
  code passes; a foundation code passes; an undeclared code, a duplicate and a common code each
  refuse registration with one diagnostic.

### Phase 2. The common set and publication

- `Dispatch::COMMON_REFUSALS` (D3), derived from what dispatch raises today: walk `resolve`,
  `check_params!`, `check_json!`, `check_approval!`, `refuse_if_busy!`, `read_request!`,
  `retained_outcome` and the operation runner, and list each code by the kinds that reach it.
- `API.discover` adds `common_refusals`. `operation_description` adds `refuses` (with each code's
  owner and description, from the registry or a foundation description) and `common_refusals_kind`.
- `tools/api_reference/api_reference.rb`: `operation_section` prints "Refuses:" with the list; a new
  short section prints the common sets once. `make fixtures` regenerates `docs/API_REFERENCE.md`.
- Tests: `API.describe` of a Windows Type action returns its list and kind; `discover` carries the
  common sets; `tests/api_reference_test.rb` fails when a described operation lacks the line.

### Phase 3. The audit hook and the built-in declarations

- `Dispatch#coded_outcome` takes the declaration (nil where none resolved, as for a malformed
  request). A module-level `Dispatch.refusal_audit` callable, nil by default, receives
  `(declaration, code)` for every refusal. Production behavior is unchanged.
- `tests/test_helper.rb` installs a recording collector. A scratch run of the full offline suite
  produces the observed `(operation, code)` pairs. These seed each operation's list; each pair is
  checked against source before it is written down, since a test can exercise a path a caller never
  reaches. The scratch script stays out of the repository.
- Declarations live beside each feature's `codes.rb`, as named arrays reused across registrations
  (Windows already groups `window.*` and `window_type.*`; loops that register many operations share
  one array). Pass-through codes count: an operation that calls a dependency's query, locator or
  participant lists the `target.*` or `reference.*` code that dependency raises.
- Order: library foundation feature, Zones, Assemblies, Windows, Colour-by and record queries.
  One commit per feature keeps each review bounded.

### Phase 4. Enforcement

- The test collector switches from recording to failing (D4): an undeclared refusal fails the test
  that produced it, naming the operation and the code.
- The `refuses:` default is removed; registration refuses an operation without one (D1).
- Gaps found here are fixed by declaring the code, never by suppressing the check.

### Phase 5. Documents

- `context/CONTRACTS.md`, "Outcomes and codes": the `refuses:` keyword, the common sets and where
  they are published, `FOUNDATION_CODES` as the checked mirror of the table, and the rule that a
  refusal outside an operation's declared and common codes is a defect.
- `context/EXTENSIBILITY.md`, the registration contract: `refuses:` is required, with an example from
  a small feature, and how the offline suite checks it.
- `context/AGENT_INTERFACE.md`, "Discover before acting": an agent reads `refuses` from `describe`
  instead of learning codes by trying.
- `docs/API_QUICKSTART.md`: one line in the conflict-recovery step pointing at `refuses`.
- README of this packet: "When to schedule" points at this plan.

## Verification

- `API.describe` of a Windows Type action lists its refusal codes and its common set (README).
- Registration refuses an operation naming an undeclared code (README).
- `make fixtures-check`: `docs/API_REFERENCE.md` changes only by the per-operation "Refuses:" lines
  and the one common-set section (README, as adjusted by D3).
- With enforcement on, the full offline suite passes; deliberately raising an undeclared code from a
  test handler fails with the operation and code named.
- No host gate: nothing here touches SketchUp behavior. Review per the ladder: this changes a public
  contract and registration, so one stronger independent pass (fresh-context Opus or
  `codex-review`) with the architecture review rubric, not a routine diff review.

## Risks

- About 130 lists are a large one-time review. Seeding from the recorded suite makes it mechanical;
  the source check per pair is the part that takes time.
- Coverage-based completeness misses a code no test reaches. That path is also untested behavior,
  and the collector makes the gap visible the first time a test reaches it.
- `FOUNDATION_CODES` duplicates the CONTRACTS.md table by design; the equality test keeps them
  together.
